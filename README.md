# Hyperflix Data Lake

This project materializes a local three-zone Data Lake from MongoDB Atlas using Python, PyMongo, Pandas and Parquet.

## Architecture

```text
MongoDB Atlas (read-only)
        |
      PyMongo
        v
  raw/ -> processed/ -> curated/ -> BI
```

The analytical model built on top of that Data Lake is a star schema in MongoDB Atlas, and the `ETL Pipeline: MongoDB Atlas -> Google BigQuery` section migrates it to the corporate Data Warehouse in Google BigQuery.

```text
MongoDB Atlas (OLTP + DW)  ->  ETL  ->  Google BigQuery (OLAP)
```

The real source domain is Hyperflix consumption, not sales. Therefore, the academic `FACT_VENTAS`, `DIM_CLIENTE` and `DIM_PRODUCTO` concepts are mapped without inventing data:

| Academic concept | Hyperflix implementation |
| --- | --- |
| FACT_VENTAS | `fact_reproducciones.parquet` |
| DIM_CLIENTE | `dim_usuario.parquet` |
| DIM_PRODUCTO | `dim_contenido.parquet` |
| DIM_FECHA | `dim_fecha.parquet` |
| Sales analytical view | `consumo_analitico.parquet` |

## Requirements

- Python 3.8 or newer (Python 3.12 recommended)
- A MongoDB Atlas database with read access
- Collections generated by the existing Hyperflix scripts, or equivalent collections configured through `.env`

## Quick Start (Automated DevOps & IaC Setup)

Hyperflix provides an automated environment and infrastructure orchestrator (`iac_setup.py`) that provisions the entire local environment in a single command:

```powershell
python iac_setup.py
```

The orchestrator executes 5 automated phases:
1. **Validación del Entorno**: Verifies Python version compatibility.
2. **Aislamiento**: Provisions the virtual environment in `env` (isolated dependency jail).
3. **Gestión de Dependencias**: Installs and upgrades all required packages from `requirements.txt`.
4. **Provisionamiento Local (Data Lake)**: Generates the 3-zone architecture (`raw/`, `processed/`, `curated/` + streaming/spark zones).
5. **Health Check**: Validates the `.env` configuration and verifies live connectivity to the MongoDB Atlas cluster (`hyperflix_db`).

To activate the isolated environment manually after setup:
```powershell
# Windows
.\env\Scripts\activate

# Linux / macOS
source env/bin/activate
```

Copy `.env.example` to `.env` and replace the placeholder URI. Never commit `.env` or print the full URI in logs. The current URI in the workspace should be rotated if it has been shared outside the local machine.

## Run

```powershell
python data_lake.py
```

The pipeline creates or reuses these directories:

```text
data_lake/
  raw/
  processed/
  curated/
```

RAW contains one Parquet snapshot per configured source collection and applies no business filters. BSON identifiers are converted to stable strings only for storage compatibility. PROCESSED is rebuilt from RAW and filters completed reproduction events when an `estado` field exists. It also derives date parts and `fecha_procesamiento`. CURATED is rebuilt from PROCESSED/RAW and contains facts, dimensions and an integrated analytical dataset. The run also reports duplicate event keys, null fact keys and orphan user/content references.

All Parquet files use the PyArrow engine, Snappy compression and `index=False`. Re-running the command overwrites local derived files deterministically; it does not insert, update, merge or delete data in Atlas.

## Configuration

The following variables are supported:

- `MONGO_URI`: required Atlas connection string.
- `MONGO_DB_NAME`: database name, default `hyperflix_db` for compatibility with the existing project.
- `DATA_LAKE_ROOT`: local output directory, default `data_lake`.
- `MONGO_BATCH_SIZE`: cursor batch size, default `1000`.
- `MONGO_USER_COLLECTION`: user/customer collection.
- `MONGO_CONTENT_COLLECTIONS`: comma-separated content collections.
- `MONGO_SUBSCRIPTION_COLLECTION`: subscription collection.
- `MONGO_PAYMENT_COLLECTION`: payment collection.
- `MONGO_EVENT_COLLECTION`: event/fact collection.

## Validation

Run a syntax check without contacting Atlas:

```powershell
python -m py_compile data_lake.py conexion.py
```

After a successful Atlas run, verify the outputs and compression metadata:

```powershell
python -c "import pathlib, pandas as pd; files=list(pathlib.Path('data_lake').rglob('*.parquet')); print(len(files)); print([(str(p), len(pd.read_parquet(p))) for p in files])"
```

Run the pipeline twice. The second run should reuse the directories and replace the local snapshots without creating duplicate rows. The pipeline reports file counts and byte sizes for each zone.

## Streaming and CDC

The streaming phase uses MongoDB Change Streams as the Kafka Consumer equivalent and Python micro-batches as the Spark Streaming equivalent. It is intentionally separate from the batch snapshot pipeline.

Configure the CDC variables in `.env` and start two terminals:

```powershell
# Terminal 1
python streaming_ingesta.py

# Terminal 2
python generar_eventos_streaming.py --once
```

For continuous reproduction inserts:

```powershell
python generar_eventos_streaming.py --interval 2
```

The consumer watches `reproducciones`, `suscripciones`, `pagos` and the temporary `STREAMING_TEMP_COLLECTION`. It handles `insert`, `update` and `delete`, persists raw events under `data_lake/raw/cdc/`, processed events under `data_lake/processed/streaming/`, alerts and metrics under `data_lake/curated/streaming/`, and stores the last resume token in `data_lake/streaming/checkpoint.json`.

The producer's `--once` mode updates a generated reproduction and creates/deletes one document only in `streaming_cdc_demo`. It never deletes historical documents from `reproducciones`. Change Streams require a MongoDB Atlas replica set deployment and a database user with permission to open streams. The consumer provides at-least-once processing with deduplication and resumes after a persisted checkpoint.

The current schema does not contain rentals, precise geolocation or continuous-session hours. Alerts therefore use high-value `pagos.monto` thresholds by currency, 4K reproduction quality and available reproduction duration without inventing missing business data.

## PySpark Big Data Jobs

The PySpark phase reads the existing curated fact and dimensions and writes independent outputs under `data_lake/curated/spark_jobs/`:

```text
curated/spark_jobs/
  metricas_contenido/
  segmentacion_usuarios/
  tendencias_temporales/
    mensual/
    diaria/
  pagos_resumen/mensual/
```

Run the three jobs with:

```powershell
$env:SPARK_LOCAL_HOSTNAME = "localhost"
$env:SPARK_LOCAL_IP = "127.0.0.1"
python scripts/spark_jobs.py
```

Job 1 explodes movie genres from their JSON representation and calculates viewing popularity. Job 2 profiles users by engagement using Spark `when` rules. Job 3 produces daily/monthly consumption trends and a separate monthly payment summary by currency. Subscription payments are never attributed to individual reproductions or content because that would duplicate revenue.

The job uses Spark `local[*]`, eight shuffle partitions, UTC timestamps and Snappy Parquet. Spark writes directories containing `part-*.parquet` and `_SUCCESS`; this is normal Spark output. Re-running the command uses `overwrite` for deterministic results.

On Windows, this workspace is configured with `HADOOP_HOME=C:\tools\hadoop-3.3.6` and `winutils.exe` under `C:\tools\hadoop-3.3.6\bin`. If setting up another machine, configure an equivalent Hadoop Windows directory before running the job. The transformations and tests can run without that binary, but the full output job requires a valid Java 17+ installation plus Hadoop Windows support. Linux, WSL or CI environments with Hadoop support do not need this Windows-specific setup. The binary is a local development prerequisite and is not committed to the repository.

The existing Pandas ETL may write nanosecond Parquet timestamps. `scripts/spark_jobs.py` enables Spark's legacy nanosecond reader and converts those values to UTC timestamps before aggregation.

## Data Warehouse in MongoDB Atlas

The warehouse phase builds a MongoDB star schema from the operational Hyperflix collections. Run it after the source data and batch transformations are available:

```powershell
python scripts/data_warehouse_builder.py
```

The builder manages only these analytical collections and does not drop operational data:

```text
dim_tiempo
dim_usuario
dim_contenido
fact_visualizaciones
```

The fact collection keeps one document per source reproduction and contains only source keys plus playback measures and operational event attributes needed for analysis. `dim_usuario` includes a user profile and completed subscription-payment totals aggregated independently by user. Payments are not joined to individual reproductions, preventing monthly subscription charges from being duplicated across views. `dim_contenido` unifies movies and TV channels, while `dim_tiempo` is generated from UTC reproduction dates.

The builder is idempotent for full loads: it drops and rebuilds only the four warehouse collections, uses `$merge` with replacement semantics, enables `allowDiskUse=True` on every aggregation, creates analytical indexes and validates fact-to-dimension references before printing success. The fact table keeps only identifiers, foreign keys and the numeric `minutos_reproducidos` measure; descriptive fields remain in dimensions. The current Atlas execution produced 368 time records, 5,000 users, 1,100 content records and 24,005 reproduction facts.

This is a MongoDB dimensional warehouse, separate from the local Parquet Data Lake and from the CDC collections. The warehouse script writes to Atlas by design; review the target database before running a full rebuild.

## ETL Pipeline: MongoDB Atlas -> Google BigQuery

The cloud phase migrates the Hyperflix star schema from the Atlas analytical warehouse into the corporate Data Warehouse hosted in Google BigQuery. It separates the transactional store (MongoDB / OLTP) from the analytical store (BigQuery / OLAP):

```text
MongoDB Atlas (hyperflix_db)   --Extract-->   Pandas   --Transform-->   BigQuery
   dim_tiempo         (368)                    typing / cleaning       hyperflix_dw.dim_tiempo
   dim_usuario      (5,000)                    rules                   hyperflix_dw.dim_usuario
   dim_contenido    (1,100)                                           hyperflix_dw.dim_contenido
   fact_visualizaciones (24,005)                                     hyperflix_dw.fact_visualizaciones
```

Run it with:

```powershell
python scripts/etl_mongo_to_bigquery.py --dry-run   # extract + transform, no writes
python scripts/etl_mongo_to_bigquery.py             # full load
```

The script creates the four destination tables with an explicit canonical schema, loads them with `WRITE_TRUNCATE` (idempotent: re-running never duplicates rows), and then reconciles the Atlas document counts against the BigQuery row counts plus the fact-to-dimension referential integrity.

The pipeline reads everything from `.env`; no credential is hardcoded in the script.

| --- | --- | --- |

| `BIGQUERY_PROJECT_ID` | read from the credentials file | Target GCP project. |

| `ETL_BATCH_SIZE` | `1000` | Cursor batch size used during extraction. |

The service account (`hyperflix-etl@hyperflix-512315.iam.gserviceaccount.com`) needs the **BigQuery Data Editor** role on the dataset and **BigQuery Job User** on the project. The credentials file is a private key and is ignored by Git.

### Type mapping

BigQuery is strict about types, so the transformation phase applies explicit rules instead of relying on inference:

| MongoDB (BSON) | BigQuery | Rule |
| --- | --- | --- |
| `ObjectId` (`_id`, `usuario_id`, `contenido_id`, `suscripcion_id`, `visualizacion_id`) | `STRING` | Serialized to its 24-character hex representation. |
| `{"ifNull": [value, default]}` | `INTEGER` | The MongoDB builder writes `{"ifNull": [...]}` inside a `$project`, which MongoDB stores as a literal subdocument instead of applying the `$ifNull` operator. The ETL unwraps it, so `dim_usuario.total_pagado` and `pagos_completados` arrive as numbers. |
| `trimestre` (`3.0`, float) | `INTEGER` | Cast from the `$ceil` of a division. |
| `generos` (array of strings) | `ARRAY<STRING>` | Normalized to a list of strings, empty for TV channels. |
| `categoria`, `anio_lanzamiento`, `duracion_minutos` (`null` for TV channels) | `STRING` / `INTEGER` | Kept nullable, never coerced to empty or zero. |
| `fecha`, `fecha_registro` (BSON date) | `TIMESTAMP` (UTC) | Cast with `utc=True` so no timestamp is shifted. |
| `activo`, `disponible`, `es_fin_de_semana` | `BOOLEAN` | Cast to the nullable `boolean` dtype. |

`dim_tiempo` is the only table whose `_id` is the business key itself (`fecha_id`), so both are unified into a single `STRING` column.

### Destination model

```text
hyperflix_dw.dim_usuario           (5,000)   clustering: pais
hyperflix_dw.dim_contenido         (1,100)   clustering: content_type   (generos: ARRAY<STRING>)
hyperflix_dw.dim_tiempo              (368)   clustering: anio
hyperflix_dw.fact_visualizaciones (24,005)   clustering: usuario_id, contenido_id
```

`fact_visualizaciones` keeps only keys, foreign keys and the `minutos_reproducidos` measure. The `fecha` column is derived from `dim_tiempo` with a 1:1 join on `fecha_id`; it does not change the grain of the fact and is the column used for range partitioning when it is enabled. As in the MongoDB warehouse, subscription payments are never attributed to an individual reproduction: `dim_usuario.total_pagado` remains a per-subscriber aggregate.

The legacy `reproducciones_analitica` collection is intentionally **not** migrated. It is the flat OLAP view of the previous phase, it was replaced by the star schema, and loading it would duplicate the fact table and break the dimensional integrity.

### BigQuery sandbox limitation: partition expiration

The GCP project used by Hyperflix runs on the BigQuery free tier (sandbox mode, billing disabled). In that mode BigQuery applies an **automatic 60-day partition expiration** when a partitioned table is created, and it also rejects any table update (`PATCH`), so the layout cannot be corrected afterwards.

The reproduction history of Hyperflix spans 368 days, so an expired partitioned fact table would silently keep only the last 60 days of data (1,240 of 24,005 rows in the observed run). The pipeline therefore:

- keeps the fact table **unpartitioned by default** (`ETL_FACT_PARTITIONING=false`), which preserves the complete history;
- reconciles the row counts after every load, so any row loss is detected and reported instead of passing unnoticed;
- degrades gracefully when a table update is rejected: the physical layout is a warning, not a pipeline failure.

With billing enabled, set `ETL_FACT_PARTITIONING=true` and run once with `--recreate-tables` to obtain the partitioned layout. Clustering is always applied because it never drops data.

### Command line options

```powershell
python scripts/etl_mongo_to_bigquery.py --only dim_usuario,dim_contenido
python scripts/etl_mongo_to_bigquery.py --write-disposition WRITE_APPEND
```

`--dry-run` performs the full extraction and transformation without contacting BigQuery, which is the fastest way to validate a change in the typing rules.

## OLAP Monitoring Dashboard

Run the final monitoring and benchmarking phase with:

```powershell
python scripts/dashboard_monitoreo.py
```

The script verifies compound indexes, executes ten `allowDiskUse=True` aggregation benchmarks and writes `dashboard_output/dashboard_monitoreo_YYYYMMDD.png`. The queries cover monthly consumption, subscription payments, content/gender popularity, city usage, device/plan performance, weekday trends, abandonment by plan, VIP users, quarterly trends, regional retention and viral content.

The dashboard adapts the academic rental metrics to Hyperflix. Payments are reported as completed subscription charges by period/currency and are never assigned to an individual reproduction or title. Optional cost chart values can be configured with `DASHBOARD_ATLAS_MONTHLY_COST` and `DASHBOARD_OPERATIONS_MONTHLY_COST`; when both are zero, the dashboard explicitly displays `No configurado` instead of inventing a cost estimate.

## Infrastructure as Code (Terraform & Automation)

The platform infrastructure is defined declaratively using **Terraform** with the official `mongodb/mongodbatlas` provider and managed via an automation CLI (`scripts/infra_manager.py`).

### Architecture

- **Project & Cluster**: Provisions a MongoDB Atlas Project and a Replica Set cluster (`M0` Free Tier on AWS `US_EAST_1` by default for academic development; configurable up to `M10+`).
- **Database Users**: Enforces least-privilege security by creating separate database users: `hyperflix_app` (readWrite on `hyperflix_db` + oplog/admin read for Change Streams) and `data_lake_reader` (read-only for analytical extraction).
- **Network Security**: Configures CIDR IP access lists (`0.0.0.0/0` default for academic labs).
- **Environment Auto-Sync**: Automatically renders `.env.terraform` upon apply with the exact connection strings and variables required by `conexion.py`, `data_lake.py`, and `streaming_ingesta.py`.

### Automation CLI Commands

1. **Check Prerequisites**:
   ```powershell
   python scripts/infra_manager.py check-tools
   ```

2. **Validate HCL Syntax**:
   ```powershell
   python scripts/infra_manager.py validate
   ```

3. **Plan & Provision Infrastructure**:
   Copy `terraform/terraform.tfvars.example` to `terraform/terraform.tfvars`, populate your Atlas API keys, and run:
   ```powershell
   python scripts/infra_manager.py plan
   python scripts/infra_manager.py apply
   ```

4. **Teardown**:
   ```powershell
   python scripts/infra_manager.py destroy
   ```

## Data Discovery y Catálogo de Datos

El gobierno de datos y 'Data Discovery' automatizado se implementa a través de [`scripts/generar_catalogo.py`](scripts/generar_catalogo.py).

El script inspecciona dinámicamente la base de datos MongoDB Atlas de Hyperflix, realiza ingeniería inversa sobre todas las colecciones activas, aplana estructuras BSON anidadas, clasifica arquitectónicamente las colecciones (OLTP, OLAP, Data Warehouse), detecta claves primarias/foráneas e índices, y enriquece los metadatos con el diccionario de negocio del streaming.

### Generar Catálogo en Excel

```powershell
python scripts/generar_catalogo.py
```

Opcionalmente, especifica una carpeta de salida personalizada:
```powershell
python scripts/generar_catalogo.py --output-dir dashboard_output
```

El script genera un libro de cálculo Excel formateado profesionalmente (`Catalogo_Datos_Hyperflix_YYYYMMDD.xlsx`) con dos pestañas:
1. **`Resumen Arquitectónico`**: Inventario de colecciones, clasificación arquitectónica (OLTP / OLAP / DW), conteo total de documentos y tamaño estimado.
2. **`Diccionario de Datos`**: Desglose a nivel de campo con tipo de dato normalizado, banderas de Primary Key (`_id`), Foreign Key (`*_id`), campos indexados y descripción semántica orientada al negocio de streaming de Hyperflix.

## Known limitations

- The pipeline uses Pandas DataFrames for transformations. Cursor batching limits MongoDB fetch batches, but a very large collection can still require substantial local memory during Parquet materialization.
- The unified content dimension combines movies and TV channels and preserves their source-specific columns.
- The legacy `reproducciones_analitica` Atlas collection is not used as the curated source; curated datasets are generated locally from source snapshots.
